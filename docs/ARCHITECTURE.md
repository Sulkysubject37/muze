# System Architecture of the MUZE Framework

## 1. Architectural Overview

MUZE (Mutator Utility for Zero-memory-fault Evaluations) is a specialized mutation testing orchestrator engineered for computational biology software. Bioinformatics codebases routinely execute floating-point simulations, probabilistic graphs, heuristic alignment passes, and statistical optimizations where developer-written assertions often fail to distinguish between structural process completion and mathematical correctness.

MUZE addresses the fundamental scalability and language-heterogeneity hurdles of bioinformatics software testing through an $O(1)$ modular orchestration architecture implemented natively in Zig (0.16.x).

```
                                  [ Source Repository ]
                                            │
                                  [ Tree-sitter Parser ]
                                  (C / C++ / Rust FFI)
                                            │
                                   [ Mutation Engine ]
                                  (Generic & Bio Ops)
                                            │
                        ┌───────────────────┴───────────────────┐
                        ▼                                       ▼
             [ Trivial Compiler Equivalence ]          [ Syntax Invalidation ]
             (Cryptographic Object Hashing)             (Compiler Rejection)
                        │                                       │
                        ▼                                       ▼
             [ Valid Mutant Candidate ]                       Discard
                        │
                        ▼
             [ Worker Pool Orchestrator ]
             (Symlinked Target / Lib Injection)
                        │
                        ▼
             [ Dual-Oracle Verification ]
      ┌─────────────────┴─────────────────┐
      ▼                                   ▼
[ Process Status / Crash ]     [ Mathematical / Bio Divergence ]
```

## 2. Multi-Language Abstract Syntax Tree (AST) Lowering

Rather than relying on brittle regular expressions or slow compiler plugins, MUZE implements direct AST token manipulation across multiple source languages via C-FFI bindings to Tree-sitter grammars:
- **C:** `vendor/tree-sitter-c`
- **C++:** `vendor/tree-sitter-cpp`
- **Rust:** `vendor/tree-sitter-rust`

### AST Lowering Mechanism (`src/ir/lower.zig`, `src/ts/runtime.zig`)

1. **Tree Generation:** Source files are ingested into memory buffers and lowered into an immutable AST structure (`ts.ts_parser_parse_string`).
2. **Grammar Symbol Extraction:** Syntax nodes are traversed recursively to extract semantic token spans. Crucially, grammar-specific nodes—such as `field_identifier` in C/C++ or `identifier` / `type_identifier` in Rust—are normalized into a unified intermediate representation (`src/ir/kinds.zig`).
3. **Lexical Splicing (`src/patch/splice.zig`):** Mutants are generated by taking original source buffers and executing surgical byte-level replacements at precise start and end byte offsets (`start_byte`, `end_byte`), preserving surrounding code formatting and comments.

## 3. The $O(1)$ Modular Orchestrator

Monolithic bioinformatics tools often require tens of minutes to recompile in continuous integration pipelines (e.g., GROMACS CMake configurations or IQ-TREE 3 multi-library builds). Recompiling entire projects for thousands of mutants is computationally intractable. 

MUZE bypasses full rebuild overhead through targeted, $O(1)$ incremental linkage:

### C and C++ Module Archive Injection
1. **Compilation Database Extraction:** The compilation flags for each target file (e.g., `-O3 -DHAVE_CONFIG_H -std=c++14`) are extracted once from the tool's build manifest (`compile_commands.json` or native build logs).
2. **Isolated Object Recompilation:** When a mutation is injected into `file.cpp`, only that specific translation unit is compiled to a temporary object file (`file.o.tmp`).
3. **Static Archive Updating:** The tool's primary static library archive (`.a`) is updated in-place using `ar csru` or `ar rcs`, replacing only the single mutated object member.
4. **Relinking:** The final test binary is relinked directly against the updated archive and required system libraries (`-lm -lz -lpthread -lbz2`), reducing compilation overhead from minutes to sub-second durations (0.15s–0.45s per mutant).

### Rust Incremental Target Symlinking
For Rust codebases (e.g., Salmon), Cargo's dependency graph involves 250+ dependency crates. Rebuilding in worker isolation directories typically triggers redundant dependency compilation.
1. **Target Cache Symlinking:** Worker workspaces symlink `target/` directly to the pre-built, cached dependency target directory.
2. **Debug Profile Compilation:** Mutants are compiled in debug mode (`cargo build -p salmon-cli`), eliminating LLVM Link-Time Optimization (LTO) overhead while generating bitwise identical scientific quantification outputs.
3. **Sub-second Incremental Builds:** Worker compilation drops from ~60s down to 0.44s–5.5s per mutant.

## 4. Concurrency, Worker Isolation, and Safety Guarantees

MUZE scales across multicore architectures using a concurrent worker pool (`src/main.zig`):

- **Worker Directories (`runs/<tool>/worker_N`):** Independent directory sandboxes prevent file contention during multi-threaded execution.
- **Deterministic Source Restoration:** Sequential evaluation inside worker threads risks cross-mutant contamination if a previous mutant leaves modified code on disk. MUZE enforces deterministic source restoration via a Zig `defer` block immediately wrapping each evaluation cycle:
  ```zig
  defer std.Io.Dir.cwd().writeFile(ctx.io, .{ .sub_path = work_file, .data = entry.source }) catch {};
  ```
  Every mutated file is restored to its exact unmutated baseline buffer before the next mutant is evaluated.
- **Deadlock and Infinite Loop Watchdogs:** Algorithmic corruptions in graph traversals or likelihood iterations can induce non-terminating loops. MUZE wraps child process execution with strict OS-level watchdog timers (10s–30s timeouts), classifying deadlocks deterministically as timeouts.

## 5. Trivial Compiler Equivalence (TCE) Engine

Syntactic mutations that are optimized into identical machine instructions skew empirical survival metrics. MUZE implements cryptographic Trivial Compiler Equivalence filtering (`src/oracle/tce.zig`):
1. The unmutated baseline module is compiled at `-O Debug` or `-O2`, and its object code (`.o`) is cryptographically hashed (SHA-256).
2. For each generated mutant, the resulting object code is compiled and hashed.
3. If the mutant object hash matches the baseline object hash, the mutant is flagged as compiler-equivalent and discarded prior to test suite execution, guaranteeing that only semantically distinct logic faults enter evaluation.

## 6. Dual-Oracle Verification Model

To evaluate developer assertions against mathematical reality, MUZE supports dual-oracle execution:
- **Oracle A (Differential IPC Oracle):** Executes mutants against a fixed input vector and compares serialized binary output packets directly against unmutated reference outputs. Any single-bit divergence triggers a differential kill.
- **Oracle B (Developer Test Suite Oracle):** Executes the standard developer test assertions or integration test harnesses. Non-zero exit codes or assertion failures trigger a test kill.
- **Categorical Matrix:**
  - *Strong Kill ($d \land t$):* Mathematical corruption detected by test assertions.
  - *Silent to Tests ($d \land \neg t$):* Mathematical corruption that completely bypasses test assertions.
  - *Assertion Only ($\neg d \land t$):* Test failure without mathematical output divergence.
  - *Full Escape ($\neg d \land \neg t$):* Mutual survival.
